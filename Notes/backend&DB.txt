4. What each PostgreSQL setting means
Service name
postgres:

This is the Docker Compose service name.

Other services in the same Compose project will later be able to reach PostgreSQL using:

postgres

as the hostname.

For example:

jdbc:postgresql://postgres:5432/nexus

Inside Docker Compose, the service name acts like a DNS hostname.

Image
image: postgres:17

This tells Docker to use the official PostgreSQL version 17 image.

A custom PostgreSQL Dockerfile is not needed because the official image already contains PostgreSQL and its startup logic.

Environment variables
environment:
  POSTGRES_DB: ${POSTGRES_DB}
  POSTGRES_USER: ${POSTGRES_USER}
  POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}

The ${...} syntax tells Compose to read the values from the root .env file.

These variables are mainly used during first-time database initialization.

They create:

A default database
A PostgreSQL user
A password for that user

Important behavior:

POSTGRES_DB
POSTGRES_USER
POSTGRES_PASSWORD

only initialize a new, empty PostgreSQL data directory.

Changing them later does not automatically update an existing database stored in the named volume.

Port mapping
ports:
  - "127.0.0.1:5432:5432"

The format is:

host-address:host-port:container-port

This mapping means:

127.0.0.1
Only expose PostgreSQL on the local computer

5432 on the host
Port used by DBeaver and local tools

5432 in the container
Default PostgreSQL port

Binding to 127.0.0.1 prevents PostgreSQL from being exposed directly to the wider local network.

DBeaver connects using:

Host: localhost
Port: 5432
Database: value of POSTGRES_DB
Username: value of POSTGRES_USER
Password: value of POSTGRES_PASSWORD
Named volume
volumes:
  - postgres_data:/var/lib/postgresql/data

PostgreSQL stores its database files inside the container at:

/var/lib/postgresql/data

The named volume:

postgres_data

stores those files outside the lifecycle of the container.

This means the database survives container deletion and recreation.

The volume declaration appears at the bottom:

volumes:
  postgres_data:
Health check
healthcheck:
  test:
    - CMD-SHELL
    - pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}
  interval: 5s
  timeout: 5s
  retries: 5

pg_isready checks whether PostgreSQL is ready to accept connections.

The settings mean:

interval: 5s
Run the check every five seconds

timeout: 5s
Allow each check five seconds to finish

retries: 5
Mark the container unhealthy after five failed checks

A running container and a ready database are not always the same thing. The health check confirms that PostgreSQL has completed startup.

7. PostgreSQL volume behavior

Stopping and removing containers while preserving data:

docker compose down

This removes the containers and Compose network but keeps named volumes.

Starting PostgreSQL again:

docker compose up -d postgres

reuses the existing database data.

Deleting the development database completely:

docker compose down -v

The -v flag also removes the named volumes.

Recreate an empty development database:

docker compose down -v
docker compose up -d postgres

This causes the PostgreSQL image to run first-time initialization again using the current .env values.

This reset procedure is appropriate for development, not production.

8. DBeaver usage

Reviewing migration results
Inspecting data

DBeaver should not be used to manually make permanent schema changes that belong in source control.

For example, permanent changes such as these should not be created manually in DBeaver:

Adding foreign keys
Adding indexes
Renaming columns
Dropping constraints

Those changes should be implemented through Flyway migrations.

Tomcat is a Java web server and servlet container.

Its main job is to:

Listen for HTTP requests
Accept network connections
Pass requests into the Spring application
Receive the result from Spring
Send HTTP responses back to clients

Example flow:

Tomcat on port 8080
        |
        v
Spring Boot controller
        |
        v
Service and database logic
        |
        v
JSON response
        |
        v
Tomcat sends response to client
19. Why Tomcat appeared in the logs

The dependency:

<artifactId>spring-boot-starter-web</artifactId>

includes embedded Tomcat by default.

“Embedded” means Tomcat is included as part of the Spring Boot application.

A separate Tomcat installation is not needed.

When the application starts, Spring Boot starts Tomcat automatically.

20. Tomcat versus Spring Boot

They are not the same thing.

Tomcat
Handles HTTP connections and web-server behavior

Spring Boot
Provides the application framework and starts/configures Tomcat

Your Java code
Contains Nexus business rules and application behavior

Tomcat does not know what an application, category, user, or favorite means.

It only handles the web transport layer.

Spring Boot maps incoming HTTP requests to application code.

24. Why the Java base image is needed

The Java version selected in Spring Initializr configures how the project is compiled.

It does not install Java inside Docker.

A container has its own isolated filesystem and cannot automatically use Java installed in WSL.

Therefore, the Docker image must include Java.

The selected distribution was:

eclipse-temurin

This is a Java distribution maintained by the Eclipse Adoptium project.

It is unrelated to the Eclipse IDE.

25. Why both JDK and JRE are used
JDK
Java Development Kit

Contains:

Java runtime
Java compiler
Development and build tools

Used to compile the application.

JRE
Java Runtime Environment

Contains what is needed to run the compiled application, without the full compiler toolchain.

Used in the final runtime image.

26. Multi-stage Docker build

The first stage is:

FROM eclipse-temurin:17-jdk AS build

This stage builds the JAR.

The second stage is:

FROM eclipse-temurin:17-jre

This starts a new image.

Only the JAR is copied from the first stage:

COPY --from=build /app/target/*.jar app.jar

Therefore, the final image contains:

JRE
Compiled application JAR

It does not contain the full JDK.

The JDK stage may remain in Docker’s build cache, but it is not included in the final runtime image.

27. Dockerfile line-by-line explanation
FROM eclipse-temurin:17-jdk AS build

Use Java 17 JDK and name this stage build.

WORKDIR /app

Set /app as the current directory inside the image.

COPY .mvn/ .mvn/
COPY mvnw pom.xml ./

Copy the Maven Wrapper and Maven configuration.

RUN ./mvnw dependency:go-offline

Download project dependencies before copying the source.

This improves Docker caching because dependencies do not need to be downloaded again every time only source code changes.

COPY src/ src/

Copy the Java source and resources.

RUN ./mvnw clean package -DskipTests

Build the executable JAR.

clean
Remove previous build output

package
Compile and package the application

-DskipTests
Do not run tests during this image build

Tests were run separately before the image build.

FROM eclipse-temurin:17-jre

Start a smaller runtime image.

WORKDIR /app

Set the runtime working directory.

COPY --from=build /app/target/*.jar app.jar

Copy the built JAR into the final image.

EXPOSE 8080

Document that the container listens on port 8080.

This does not publish the port by itself.

ENTRYPOINT ["java", "-jar", "app.jar"]

Start the Spring Boot application when the container runs.

Part 5: Flyway
34. What Flyway is

Flyway is a database migration tool.

It manages permanent database schema changes as version-controlled files.

Examples of schema changes Flyway should manage:

Creating tables
Adding columns
Adding indexes
Creating foreign keys
Adding unique constraints
Renaming database objects
Changing column definitions
Removing obsolete schema objects
35. Why Flyway is useful

Without migrations, developers might manually change a database through DBeaver.

That creates problems:

Changes may not be documented
Other environments may not receive the same changes
Production may differ from development
Schema changes may be applied in the wrong order
Changes may be difficult to reproduce

Flyway makes schema changes:

Repeatable
Ordered
Version controlled
Reviewable
Deployable
Consistent between environments
36. How Flyway works

Migration files are normally placed under:

backend/src/main/resources/db/migration/

Example filenames:

V1__create_initial_schema.sql
V2__add_application_indexes.sql
V3__add_user_profile_object_key.sql

Filename format:

V
Version number

__
Two underscores

Description
Human-readable migration name

.sql
SQL migration file

Example:

V1__create_initial_schema.sql

Flyway runs unapplied migrations in version order.

37. Flyway schema history table

Flyway creates its own tracking table in PostgreSQL, usually named:

flyway_schema_history

It records information such as:

Migration version
Migration description
Filename
Checksum
Execution time
Whether the migration succeeded

Before applying migrations, Flyway checks this table to determine which migrations have already run.

38. Migration workflow

A normal workflow is:

1. Decide the schema change
2. Create a new migration file
3. Write the SQL
4. Run the application or Flyway
5. Flyway applies the migration
6. Inspect the result in DBeaver
7. Run tests
8. Commit the migration with the related code

DBeaver is used to verify the result, not to create the permanent change manually.

39. Important Flyway rules

Once a migration has been applied to a shared or persistent database, do not casually edit it.

For example, after this has run:

V1__create_initial_schema.sql

a later change should normally use:

V2__modify_initial_schema.sql

rather than rewriting V1.

Flyway stores checksums. Editing an already-applied migration can cause validation errors because the file no longer matches the recorded migration.
